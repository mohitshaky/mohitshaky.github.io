p99 doubled across two releases and nobody can point at the change

Nobody shipped anything obviously slow. Mean response time barely moved. But p99 went from 400ms to 900ms across two releases, and the diff is four hundred commits. This is the diagnostic order I use, and it is deliberately not the order most teams try first.

Start with what the shape tells you. The mean staying flat while p99 doubles is itself a strong signal. It means most requests are unaffected and a minority became much slower. That rules out anything uniformly expensive — an extra field serialised on every response, a slightly slower algorithm — because those raise the whole distribution. You are looking for something that affects a subset: requests that queue, requests that touch more data than others, or requests unlucky enough to land during a pause.

That narrows it to roughly four causes, and they are worth checking in this order.

1. Connection pool saturation

The most common and the most misread. HikariCP defaults to ten connections. When all ten are in use, the eleventh request does not fail — it blocks, waiting for one to be returned. That waiting time is invisible in your database metrics, because from the database's perspective every query is still fast. The query time did not change. The time spent queuing for permission to run a query did.

This produces exactly the mean-flat-p99-doubled signature: under the pool limit everything is normal, and past it a minority of requests wait. It appears without any code change, purely from traffic growth, which is why "nobody changed anything" is often literally true.

What to look at:

  • hikaricp.connections.pending — non-zero at peak is the whole answer
  • hikaricp.connections.acquire timer — if its p99 is a meaningful slice of request p99, stop looking elsewhere
  • hikaricp.connections.usage — how long each borrowed connection is held

The instinct is to raise maximum-pool-size. Sometimes correct, often not: if connections are being held for longer than they should be — a transaction spanning an HTTP call, say, or @Transactional on a method that does far more than database work — a larger pool just moves the queue into the database. Check hold time before pool size. A pool bigger than the database's own connection limit divided by your replica count is a way to convert an application problem into a database outage.

2. N+1 access that grew with the data

A lazy association iterated in a loop issues one query per row. With ten rows in test data nobody notices. Two years later the largest customer has four thousand, and their requests — and only theirs — are catastrophically slow. Mean flat, p99 doubled.

The reason this hides so well is that it is data-dependent rather than code-dependent. The endpoint is fine for almost everyone. Bisecting releases will never find it, because no release introduced it — a customer's growth did.

The fastest way to find it: turn on statement counting per request in a staging environment and sort endpoints by query count rather than by duration. An endpoint issuing 900 queries is obvious in that view and invisible in a latency dashboard. Datasource proxies that log a per-request query count make this a five-minute exercise.

The fix is a join fetch, an entity graph, or a batch size — but confirm the count dropped rather than assuming. It is easy to add a fetch join that fixes one association and leaves a second one lazy, and the endpoint is still doing 300 queries.

3. GC pressure, especially after a heap or JDK change

Garbage collection pauses hit whichever requests are in flight when they occur. That is, by construction, a tail-latency problem: a 200ms pause every few seconds does almost nothing to the mean and a great deal to p99.

Worth checking when latency changed around an infrastructure event rather than a code release:

  • A container memory limit changed, so the JVM's ergonomic heap sizing changed with it
  • A JDK upgrade switched the default collector, or moved between G1 and Parallel by heap-size heuristics
  • Heap grew large enough that full collections became meaningfully longer
  • An added cache is retaining far more than intended and pushing objects into the old generation

Compare GC pause percentiles against request latency percentiles on the same time axis. If they move together, that is your cause. If GC is flat while p99 climbs, rule it out and move on — a great deal of time gets burned tuning collectors that were never the problem.

4. Cache hit rate decay

A cache sized for last year's key space quietly stops working as the key space grows. Hit rate slides from 95% to 60% over months. The 40% of requests that now miss go to the database, and those are your tail. Nothing was changed; the cache simply outgrew its configured size.

This is the one that most often goes undetected for longest, because a cache that is working is invisible and a cache that is degrading is equally invisible unless hit rate is actually on a dashboard. If you take one thing from this section: graph cache hit rate, and alert when it drops rather than when it is low.

The order matters more than the list

All four of these are well known. What teams get wrong is the sequence — they profile the application code first, because that is where a performance problem intuitively lives, and application code is rarely the answer to a regression of this shape. It was fast last year with the same code.

Work outside-in:

  1. Is the request queuing before it does work? Pool pending, thread pool queue depth.
  2. Is it doing more work than it used to? Query count per request, payload sizes, cache hit rate.
  3. Is something pausing the process? GC percentiles against latency percentiles.
  4. Only now, profile the code.

And measure before changing anything. The most expensive outcome of a latency investigation is not failing to find the cause — it is shipping four speculative fixes at once, watching p99 improve, and never knowing which one did it. The next regression then starts from zero.
