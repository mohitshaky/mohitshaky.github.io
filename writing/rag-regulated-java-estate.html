What a compliance review asks about your RAG service

Getting retrieval-augmented generation working takes an afternoon. Getting it past a security review at a bank takes considerably longer, and the gap is not model quality. It is four questions nobody asks a prototype — and each one has a concrete answer in code.

1. Can it answer using another customer's documents?

This is the question that ends the conversation if you cannot answer it precisely, and the failure it guards against is the nastiest kind: multi-tenant retrieval leakage does not throw. There is no exception, no error metric, no alert. One customer simply receives a fluent, well-cited answer assembled from another customer's files, and nobody finds out until someone reads an answer that mentions a company they have never heard of.

The mechanism is mundane. Every retrieval path must filter on tenant, and every ingestion path must stamp it. Miss the filter on one code path — a new endpoint, a batch reindexer, an "admin" search added for support — and that path leaks silently.

Two things make this defensible. First, apply the filter in one place, on the read side, rather than leaving each caller to remember. Second, and this is what a reviewer actually wants to see, assert it with a test that seeds two tenants and proves one cannot retrieve the other's passages — including the case where a tenant has no documents at all and must get an empty result rather than somebody else's.

A useful sharpener: run that isolation test with the similarity threshold dropped to zero, so every stored chunk is a candidate. If the tenant filter is broken, the other tenant's content comes back. If you only ever test at production thresholds, a broken filter can hide behind scoring.

2. What does it do when it does not know?

Handed weak context and asked to be helpful, a language model produces a fluent, confident, wrong answer. This is the failure mode that matters most in a regulated setting and the one demos never show, because it looks exactly like success. There is no error, no low-confidence flag, nothing in a log. Just a plausible paragraph that happens not to be true.

Prompt wording alone will not fix this. "Only answer from the context" helps and does not hold under pressure, because you have no control over whether it was followed. The reliable approach is to make refusal a deterministic decision taken before the model is called: if the best retrieved passage scores below a threshold, or too few passages survive, decline and say why. That decision is testable, and it costs nothing — no tokens are spent on a question you were never going to answer well.

Two design details matter. Return refusal as a structured field rather than as prose, so callers can branch on it without pattern-matching English. And treat the threshold as a tuning dial with a real trade-off: raise it and you refuse questions the corpus could just about answer; lower it and you start inventing. That trade needs measuring rather than guessing, which means an evaluation set that deliberately includes questions the corpus cannot answer. Scoring only answerable questions makes "answer everything" look like a perfect score.

3. Why did it say that, six months ago?

This question gets asked in regulated environments, usually by someone who is not interested in how language models work. "We have changed the prompt since then" is not an acceptable answer.

The fix is unglamorous: treat prompts as released artefacts rather than string literals. Version them as files, record which version produced each answer, and return that version with the answer. Changing a prompt then becomes adding a file and moving a config value — a reviewable diff and a revertible one, rather than an edit buried in a service class that nobody can date.

The same logic extends to what was retrieved. Storing the passage identifiers and scores that produced an answer means you can reconstruct the reasoning later, rather than re-running a query against an index that has since changed.

4. What stops the bill running away?

A per-tenant token ceiling is easy to describe and easy to get subtly wrong. The two mistakes I see most:

  • Counting in memory. An in-process counter gives every replica its own budget, so three pods means three times the ceiling. It also resets on restart. Counters have to live somewhere shared — a row in Postgres is entirely sufficient.
  • Read-modify-write in application code. Reading the total, adding to it, and writing it back loses updates under concurrency, and passes every single-threaded test you will write. Let the database do the arithmetic with an atomic upsert, and write a test that hammers it from several threads at once.

Where to check and where to record also matters. Check the budget before retrieval, so an over-budget tenant costs nothing at all; record usage after the call, from the provider's reported usage rather than an estimate. A tenant can then overshoot by at most one request, which is the right trade for a ceiling whose job is stopping runaway spend rather than billing.

The pattern underneath all four

Each of these is the same shape of problem: a failure that produces no error. Leakage returns a good-looking answer. Ungrounded generation returns a good-looking answer. An unversioned prompt works fine until somebody asks a question about the past. An in-memory budget works fine until you scale out.

That is why the answer to each is a test or a structural constraint rather than a monitor. You cannot alert on a failure that does not signal. You can only make it impossible, and then prove it.
